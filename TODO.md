The column exists (it returns null, not an error) and the identical path succeeds for `entry_reviewed_at` via `markEntryReviewed`. The defect is that the stamp is attempted exactly once, at settle, and its failure is permanent by design: `settleShipped` intentionally does not gate the ship on the stamp, and the reconciler only settles rows drawn from the `dispatched`/`running` in-flight set, so a row that reaches `shipped` with an unstamped todo is never revisited. Any transient failure in that one moment — most plausibly the startup backlog reconcile (`kickDispatchReconciler`) settling rows before `allProjects` has hydrated from Supabase, which makes `stampEntryShipped`'s in-memory scan return `{ok:false, error:'Todo not found.'}` — is unrecoverable. Fix by making the stamp a repairable invariant. Add a reconcile pass that runs wherever all queue rows are already loaded (`fetchAllQueueRows`, `agentQueueStore.js:242`, is the natural host since it needs no new fetch): for every row at `shipped` carrying a `todo_id` whose todo has no `shippedAt`, call `listLogic.stampEntryShipped(todo_id)`. `stampEntryShipped` is already idempotent — an already-stamped todo keeps its original time — so this is safe to run on every load and needs no separate migration for the existing 26 rows; they repair on the next pass. Gate the pass on todos actually being hydrated so it cannot re-run the same failed lookup: skip and retry on the next load rather than warning per row. Keep the ship un-gated on the stamp — that decision is correct and its comment explains why; this entry changes only whether a missed stamp is recoverable. Do NOT make the reconciler re-settle already-shipped rows to achieve this: settling has other effects (PR link resolution, `refreshQueueAndNotify`) and re-running it would be a far wider change than stamping a missing field. Do NOT touch `derivePhase` — its gates are correct and the fix is to populate the field they read. While implementing, confirm the transient cause: the failure path logs `settleShipped: failed to stamp shipped_at on todo <id>: <reason>`, so report in the PR body which reason actually fires, since the answer determines whether a follow-up entry is needed to order the boot sequence.
