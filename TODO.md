- [x] **[HIGH]** Arm the dispatch reconciler on a local dispatch, not only on a realtime push — Completed: 2026-07-30
  - Type: bug
  - Description: A run dispatched in-session never settles until the page is reloaded, so no live surface updates — not the coverage breakdown, the tab summary, or the row badge. Only the TODO.md viewer reflects the finished run, because it reads the file directly rather than the queue store. The cause is circular: `startDispatchReconciler` arms the poller from exactly one signal, an `onQueueChange` listener calling `evaluateReconciler`. But `notifyQueueChange` is itself only fired by `refreshQueueAndNotify` after a settle. So the poller needs a notify to arm, notifies come from settles, and settles come from the poller — nothing breaks the cycle except a page load, where `kickDispatchReconciler` runs the startup backlog reconcile. That is why a refresh is the only thing that works, and why an earlier entry found the notify path already correctly implemented: it is correct, it just never gets reached.
  - Behavior: Dispatching a run from any surface — the detail pane's Dispatch or Retry, a mockup variant's Use, or Accept on a derive proposal — arms the reconciler immediately, without waiting for a realtime push or a reload. The run then settles on its own within a poll cycle of its PR merging, and every live surface updates: the row badge flips to REVIEW, the RUNNING filter count drops, the nav working dot clears, and an open coverage breakdown moves its aspect to Shipped with the covered count raised. Reloading remains a valid path but is no longer the only one.
  - Implementation notes:

Its own comment says the board's dispatch tail called it "so a run settles promptly without waiting for the interval." That call site went away with the board. Restore it: every path that writes a row to `dispatched` must call `kickDispatchReconciler` after the write resolves.
    - `dispatchDraft` in `dispatchDraft.js` is the single funnel — Dispatch, Retry, mockup Use, and proposal Accept all resolve to it. Calling it once there covers every surface and cannot be forgotten by a future caller. Prefer that over adding calls at each UI site.
    - Do NOT remove the `onQueueChange` listener. A run dispatched from another device arrives only as a realtime push, and that path must keep arming the poller.
    - Both arming paths must be safe together. `startDispatchReconciler` is guarded by `_reconcilerStarted` and `evaluateReconciler` is idempotent, but verify a local dispatch that also produces a realtime echo does not start two intervals or double-tick.
    - Fire-and-forget the kick — it must not block the dispatch's own success path or its UI feedback. A failed kick should leave the row dispatched and rely on the next reload, not surface an error over a dispatch that actually worked.
    - While fixing this, determine and report in the PR body whether a local write produces an `onQueueChange` at all. If Supabase does echo the client's own writes and the store's realtime handler is discarding them, that is a second bug worth its own entry — and it would explain more than this one symptom.
