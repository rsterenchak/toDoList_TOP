- [x] **[HIGH]** Arm the dispatch reconciler on a local dispatch, not only on a realtime push — Completed: 2026-07-30
  - Type: bug
  - Description: A run dispatched in-session never settles until the page is reloaded, so no live surface updates — not the coverage breakdown, the tab summary, or the row badge. Only the TODO.md viewer reflects the finished run, because it reads the file directly rather than the queue store. The cause is circular: `startDispatchReconciler` arms the poller from exactly one signal, an `onQueueChange` listener calling `evaluateReconciler`. But `notifyQueueChange` is itself only fired by `refreshQueueAndNotify` after a settle. So the poller needs a notify to arm, notifies come from settles, and settles come from the poller — nothing breaks the cycle except a page load, where `kickDispatchReconciler` runs the startup backlog reconcile. That is why a refresh is the only thing that works, and why an earlier entry found the notify path already correctly implemented: it is correct, it just never gets reached.
  - Behavior: Dispatching a run from any surface — the detail pane's Dispatch or Retry, a mockup variant's Use, or Accept on a derive proposal — arms the reconciler immediately, without waiting for a realtime push or a reload. The run then settles on its own within a poll cycle of its PR merging, and every live surface updates: the row badge flips to REVIEW, the RUNNING filter count drops, the nav working dot clears, and an open coverage breakdown moves its aspect to Shipped with the covered count raised. Reloading remains a valid path but is no longer the only one.
  - Implementation notes:
    - `kickDispatchReconciler` already exists and does the right thing — refresh the all-projects cache, settle stranded rows, evaluate, tick once. Its own comment says the board's dispatch tail called it "so a run settles promptly without waiting for the interval." That call site went away with the board. Restore it: every path that writes a row to `dispatched` must call `kickDispatchReconciler` after the write resolves.
    - `dispatchDraft` in `dispatchDraft.js` is the single funnel — Dispatch, Retry, mockup Use, and proposal Accept all resolve to it. Calling it once there covers every surface and cannot be forgotten by a future caller. Prefer that over adding calls at each UI site.
    - Do NOT remove the `onQueueChange` listener. A run dispatched from another device arrives only as a realtime push, and that path must keep arming the poller.
    - Both arming paths must be safe together. `startDispatchReconciler` is guarded by `_reconcilerStarted` and `evaluateReconciler` is idempotent, but verify a local dispatch that also produces a realtime echo does not start two intervals or double-tick.
    - Fire-and-forget the kick — it must not block the dispatch's own success path or its UI feedback. A failed kick should leave the row dispatched and rely on the next reload, not surface an error over a dispatch that actually worked.
    - While fixing this, determine and report in the PR body whether a local write produces an `onQueueChange` at all. If Supabase does echo the client's own writes and the store's realtime handler is discarding them, that is a second bug worth its own entry — and it would explain more than this one symptom.
    - Add a regression test that dispatches without any realtime push and asserts the poller is armed. That is the invariant the circularity broke, and it is testable without a live subscription.
    - This is the fourth failure in this chain — a marker refresh hooked to a transition nothing produced, a reconciler that only ran while the board was mounted, a notify that was already correct, and now an arming signal that can never fire on its own. Each was one layer beneath the last. Note in the PR body which surfaces were verified updating live after the fix, so the next investigation starts from a confirmed list.
  - Out of scope: The reconciler's decision logic, its poll cadence, and its give-up window. `notifyQueueChange` and `refreshQueueAndNotify`, both correct. The coverage modal's repaint handle, also correct. `aspectStatus` and `computeCoverage`. Deleting the Agent view.

- [ ] **[MEDIUM]** Treat entry_reviewed_at as proof of shipping so acknowledged tasks keep their DONE state
  - Type: bug
  - Description: Tasks that were accepted and closed render as plain rows with no completion indicator. `derivePhase` reaches `PHASE.DONE` only via `item.shippedAt` or via the entry's marker resolving to `shipped` in `TODO.md`, and checks `entryReviewedAt` only after one of those gates passes. Tasks acknowledged before the `shipped_at` column existed have no stamp, and `clear all entries` destroyed the markers they resolved against — so both gates fail and they fall through to `PHASE.NONE`. But `entry_reviewed_at` is itself sufficient evidence: acknowledging is only reachable from the ACCEPT phase, which already requires shipped-ness, so a reviewed timestamp cannot exist on a task that never shipped. Consult it as its own terminal gate.
  - Behavior: A task with `entry_reviewed_at` set resolves to `PHASE.DONE` regardless of whether `shipped_at` is stamped or its marker still exists in `TODO.md`. Rows acknowledged before the stamp existed, and rows whose entries were cleared from the file, show their completed state again. Tasks with `shipped_at` and no review still resolve to ACCEPT. Tasks with a checked marker and no review still resolve to ACCEPT. Nothing else about the phase order changes.

The queue states must keep outranking it — a re-triaged or re-dispatched task with a stale review stamp is genuinely in flight again, and showing DONE over a running row would be worse than the current bug.
